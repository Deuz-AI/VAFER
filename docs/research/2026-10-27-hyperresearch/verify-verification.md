1. **partly**: The mechanical cite-check triage auto-passes wrong numbers. It tests the sentence's numbers as substrings of the cited note's LLM-extracted claims, and those numbers include the citation index itself. Auto-passed pairs are never checked by the LLM. Probe: 'grew 5%' passes against a 25% claim, '[12]' passes because of '2012', and 86% of the example report's pairs carry their own index as a number. (evidence: core/citecheck.py:104, 144-151; core/hooks.py:3552; example-reports/rl-exploration-trajectory-planning.md)
   Evidence: citecheck.py:104 runs `"numbers": _NUMBER_RE.findall(sentence)` on the raw sentence, so the markers are included. Line 149 keeps only numbers of 2 or more characters. Line 150 is `all(n.replace(",", "") in blob.replace(",", "") for n in nums)`, where the blob (:144-147) joins claim, quoted_support and numbers across ALL of the note's claims. Auto-passed pairs never reach the LLM: sample_needs_llm (:187-189) keeps only `needs-llm` pairs, and the pairs file (:208-213) holds only `sampled_for_llm` and `dangling`, with auto-passes present only as a count. hooks.py:3552 says 'Do not re-litigate pairs the triage auto-passed.' My probes used the repo's extract_pairs and triage_pairs. 'Acme revenue grew 5% in 2020 [1].' against the claim 'grew 25% in 2020' gave supported-mechanical (numbers `['5%','2020','1']`). 'The moon is made of green cheese [12].' against a note whose only claim is 'signed in 2012' also gave supported-mechanical. For the example report I built a mock vault that maps all 97 Sources URLs. It yields 155 pairs. All 155 have their own index in their number list. Only 125 (80.6%) have an own index of 10 or more, which is what survives the length filter. 134 (86.5%) carry some index of 10 or more, either their own or a co-cited one. For 63 (40.6%), citation indexes are the only numbers of 2+ characters.
   Correction: Every part of the mechanism is right. Two numbers need fixing. (1) The 2-character filter (:149) drops single-digit indexes, so only [10] and above enter the test. In the example, 30 of 155 pairs cite [1]-[9]. (2) The reader's 86% is 134/155: pairs whose numbers contain any index of 10+, their own or a co-cited one. 'Their own index' is 125/155 = 80.6%, or 100% if single digits count. The index cuts both ways. If its digits are missing from the blob, the pair goes to the LLM, which is safe. But any number of 2+ characters turns off the 6-word branch (:152 `elif not nums`), so for a pair citing [10] or above the overlap test is never tried.

6. **partly**: Source ranking has little effect and its provenance edges point the wrong way. The quality multiplier (0.5 + quality) is applied after the SQL LIMIT, with a spread of about 1.10-1.20 for non-retracted notes. The --suggested-by breadcrumb is placed on the fetched note, so PageRank rewards the suggester rather than the primaries sources converge on (probe), contrary to the graphrank docstring. (evidence: search/fts.py:125, 181-190; cli/fetch.py:463-478; core/graphrank.py:3-7; core/quality.py:25-53)
   Evidence: The SQL applies `LIMIT ? OFFSET ?` at fts.py:125. Only afterwards does :186-190 multiply each score by `0.5 + q` and re-sort, so the re-rank only reorders the top N. The default N is 20 (core/config.py:229), and step 10 runs `search ... --ranked -j` (10-triple-draft.md:110). fetch.py:463-478 prepends `*Suggested by [[suggester]]*` to the fetched note's body. Sync stores the link with source_id set to the note whose body holds it (core/sync.py:317-328). PageRank then adds the edge as `out[src].add(dst)` (graphrank.py:36-38). A repeat fetch appends further breadcrumbs to the existing note (fetch.py:255-265, 36-85), so convergence adds out-edges FROM the primary. Probe (repo pagerank): give primary P breadcrumbs to S1, S2 and S3. S1-S3 score 1.0. P scores 0.779, the same as an unlinked note Q (0.779). With the edges reversed, P scores 1.0. graphrank.py:3-7 says centrality means 'many independent research chains converged on this source', which is the opposite of what happens.
   Correction: The re-rank after LIMIT and the inverted edges are both confirmed. The 'spread of about 1.10-1.20 for non-retracted notes' is not a property of the code. It comes from the reader's two example notes, which I reproduced: a ground-truth note with centrality 0.10 gives ×1.173, and a commentary hub with centrality 1.0 gives ×1.118. Under the default weights (config.py:115-124), a fetched, non-retracted note ranges from ×0.64 (commentary tier, other components 0) to ×1.5. A commentary note with centrality 0.05 gets ×0.77; a ground-truth note with centrality 1.0 gets ×1.5. So the multiplier can reorder the top 20. 'Little effect' holds mainly for two reasons: the LIMIT, and the inverted centrality, which cancels the tier gap when a hub is compared with a primary (that is what the reader's pair shows). Retraction is the one strong lever (×0.55).

(evidence: core/independence.py:134 `share = round(1.0 / len(members), 4)` while the root keeps 1.0 (:135); CHANGELOG.md:241 'five syndicated copies of one press release are ONE vote, not five'; skills/hyperresearch-3-contradiction-graph.md:58 'Count each cluster as ONE voice')

Missed by the reader:
- The gate never reads `cite-check-pairs.json`. In Python, only citecheck.py:214 and cli/citecheck_cmd.py:64 touch that file. Dangling citations reach the findings file only if the orchestrator appends them (14-5-cite-check.md:40, 76), and severity is whatever the LLM writes. If the orchestrator skips the append, the run ships dangling citations with a green gate.
- Sampling never takes effect for numbered reports. `strong` is True whenever `_NUMBER_RE.search(sentence)` matches (citecheck.py:105), and a citation marker always matches. In the example report, all 155 pairs are strong, 51 of them only because of the marker. So every needs-llm pair goes to the LLM, and the documented '60% of weak sentences' (cli/citecheck_cmd.py:19; CHANGELOG.md:238) never happens. Auto-passed pairs are written nowhere (citecheck.py:208-213), so there is no audit trail of what was skipped.
- quote-integrity, the gate's only check that reads source text, ignores which source is cited. A quoted span of 5+ words inside double quotes passes if it appears in ANY vault note (cli/lint.py:110-147). The match is a porter-stemmed FTS phrase query that ignores case and punctuation (core/db.py:203-209). So a real quote from source A, cited to source B, passes. Quotes under 5 words or in single quotes are not checked.
- There are more unfenced read paths. The MCP server's search_notes, read_note and read_many return raw bodies (mcp/server.py:78-80, 93-107, 122-129). The title, summary and snippet fields of `note show` and `search` sit outside the fence (cli/note.py:186-194; search/fts.py:109, 164).
- Claims are ingested only at step 2.7 (2-width-sweep.md:229). Fetchers at step 8 (8-corpus-critic.md:90-103) and step 13 (13-gap-fetch.md:69) write claims files that are never ingested. So `claims search`, the cite-checker's wrong-source lookup (core/hooks.py:3524), cannot find them, and the triage blob for those notes is empty. Ingest also drops entities, scope_conditions, time_period and region (core/claims.py:124-142), the fields step 3 matches on (3-contradiction-graph.md:35-39), so step 3 has to read the raw JSON.
